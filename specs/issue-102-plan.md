# Feature: Triggers should not ignore certain types of comments

## Feature Description
Currently, both ADW triggers (webhook and cron) ignore all issue comments on the assumption that they are generated by the agent. This means human comments on issues — such as follow-up instructions, clarifications, or priority changes — are silently ignored and never trigger a workflow.

This feature updates both triggers to distinguish between ADW-generated comments (which contain a markdown heading with an emoji icon like `:gear:`, `:rocket:`, `:tada:`) and human-authored comments (which do not). Human comments should trigger the appropriate workflow for the issue. Additionally, if an ADW workflow is already running for a given issue, the trigger should defer actioning the comment until the running workflow has completed or failed.

## User Story
As a project maintainer
I want the ADW triggers to detect and act on human comments posted to issues
So that I can provide follow-up instructions or corrections on issues without them being silently ignored by the automation

## Problem Statement
Both the webhook trigger and cron trigger treat all issue comments as agent-generated noise. The webhook only handles `issues` (action: `opened`), `pull_request_review_comment`, `pull_request_review`, and `pull_request` events — it has no handler for `issue_comment` events. The cron trigger's `isQualifyingIssue` function only qualifies issues with zero comments or where the latest comment contains "adw", effectively filtering out human follow-up comments. This means a maintainer cannot post a comment on an open issue to trigger additional work.

## Solution Statement
1. **Create a shared utility function** `isAdwComment(body: string): boolean` in `workflowCommentsBase.ts` that returns `true` when a comment body contains a markdown heading with an emoji icon (pattern: `^## :[a-z_]+: `). This is the signature of ADW-generated comments.
2. **Create a shared utility function** `isAdwRunningForIssue(issueNumber: number): boolean` that checks whether an ADW workflow is currently active (running and not yet completed/failed) for a given issue, by inspecting the issue's comments for the most recent workflow stage.
3. **Update the webhook trigger** to handle `issue_comment` events (action: `created`). When a new comment is posted that is NOT an ADW comment, and no ADW workflow is currently running for the issue, trigger the appropriate workflow. If a workflow IS running, log that the comment is deferred.
4. **Update the cron trigger** to qualify issues where the latest comment is a non-ADW human comment (i.e., does not match the emoji heading pattern). If an ADW workflow is running for the issue, skip it (defer) until the workflow completes or fails.
5. **Add comprehensive unit tests** for the new utility functions and updated trigger logic.

## Implementation Plan
### Phase 1: Foundation
Create the shared utility functions that both triggers will depend on:
1. `isAdwComment(body: string): boolean` — Returns `true` if the comment body contains a line matching `^## :[a-z_]+: ` (the ADW emoji heading pattern). This identifies comments posted by the ADW system.
2. `isAdwRunningForIssue(issueNumber: number): boolean` — Fetches the issue's comments via `fetchGitHubIssue`, scans them for ADW workflow stage comments using `parseWorkflowStageFromComment`, and returns `true` if the most recent stage is NOT a terminal stage (`completed`, `error`). Terminal stages indicate the workflow has finished.
3. Export both functions from the github module barrel.

### Phase 2: Core Implementation
Update both triggers to use the new utility functions:
1. **Webhook trigger**: Add an `issue_comment` event handler that:
   - Extracts the comment body and issue number from the payload.
   - Only processes `created` actions.
   - Calls `isAdwComment(body)` — if `true`, ignores the comment (it's from the ADW system).
   - Calls `isAdwRunningForIssue(issueNumber)` — if `true`, logs deferral and returns.
   - Otherwise, classifies the issue and spawns the appropriate workflow script.
2. **Cron trigger**: Update `isQualifyingIssue` to:
   - Return `true` if the issue has zero comments (existing behavior).
   - Return `true` if the latest comment is NOT an ADW comment (new behavior — human comment detected).
   - Keep returning `true` if the latest comment contains "adw" (existing recovery behavior).
   - Add a deferral check: before spawning a workflow for a qualifying issue, call `isAdwRunningForIssue` and skip the issue if a workflow is active.

### Phase 3: Integration
Ensure both triggers correctly handle edge cases:
- Comments that happen to contain emoji but not in the ADW heading format should be treated as human comments.
- Multiple rapid human comments should not spawn multiple concurrent workflows.
- The `processedIssues` set in the cron trigger already prevents duplicate processing within a single polling session; the deferral check prevents triggering while a workflow is active.

## Step by Step Tasks

### Step 1: Add `isAdwComment` utility to `workflowCommentsBase.ts`
- Add a new exported function `isAdwComment(commentBody: string): boolean` in `adws/github/workflowCommentsBase.ts`.
- The function should return `true` if the comment body contains a line matching the regex `/^## :[a-z_]+: /m` — this is the pattern all ADW workflow comments use (e.g., `## :rocket: ADW Workflow Started`, `## :gear: Build Progress`).
- This function is deliberately simple and regex-based so it can be used synchronously without API calls.

### Step 2: Add `isAdwRunningForIssue` utility to `workflowCommentsBase.ts`
- Add a new exported function `isAdwRunningForIssue(issueNumber: number): boolean` in `adws/github/workflowCommentsBase.ts`.
- Import `fetchGitHubIssue` from `../github/githubApi`.
- The function should:
  1. Call `fetchGitHubIssue(issueNumber)` to get the issue with its comments (this is an async function, so `isAdwRunningForIssue` should also be async and return `Promise<boolean>`).
  2. Filter comments to find ADW workflow comments using `parseWorkflowStageFromComment`.
  3. If no ADW workflow comments exist, return `false`.
  4. Sort the ADW comments by `createdAt` descending to find the most recent stage.
  5. Return `true` if the most recent stage is NOT one of the terminal stages: `'completed'`, `'error'`.
  6. Return `false` if the most recent stage is a terminal stage (workflow is done).

### Step 4: Create unit tests for `isAdwComment` and `isAdwRunningForIssue`

### Step 5: Update the webhook trigger to handle `issue_comment` events
- In `adws/triggers/trigger_webhook.ts`, add an import for `isAdwComment` and `isAdwRunningForIssue` from `../github`.
- Add a new event handler block for the `issue_comment` event, placed BEFORE the `issues` event handler.
- The handler should:
  1. Extract the action from the payload — only process `created` actions.
  2. Extract the comment body from `body.comment.body`.
  3. Extract the issue number from `body.issue.number`.
  4. Call `isAdwComment(commentBody)` — if `true`, log and return `{ status: 'ignored' }` (it's an ADW system comment).
  5. Call `isAdwRunningForIssue(issueNumber)` asynchronously — if `true`, log `"ADW workflow already running for issue #N, deferring comment"` and return `{ status: 'deferred' }`.
  6. Otherwise, log `"Human comment on issue #N, triggering ADW workflow"`, classify the issue and spawn the workflow (same pattern as the existing issue handler).
  7. Return `{ status: 'processing', issue: issueNumber }`.

### Step 6: Update the cron trigger to handle human comments
- In `adws/triggers/trigger_cron.ts`, add an import for `isAdwComment` and `isAdwRunningForIssue` from `../github`.
- Update the `isQualifyingIssue` function:
  - If issue has no comments, return `true` (unchanged).
  - Get the latest comment body.
  - If the latest comment contains "adw" (case-insensitive), return `true` (existing recovery behavior, unchanged).
  - If the latest comment is NOT an ADW comment (i.e., `!isAdwComment(latestComment.body)`), return `true` (new behavior — human comment detected).
  - Otherwise, return `false`.

## Testing Strategy
### Unit Tests
- **`isAdwComment`**: Test with various ADW comment formats (all stage types from `STAGE_HEADER_MAP`), human comments, edge cases (empty strings, emoji without heading format, headings without emoji).
- **`isAdwRunningForIssue`**: Mock `fetchGitHubIssue` to return issues with different comment combinations. Test terminal stages (`completed`, `error`) return `false`, and active stages (`starting`, `implementing`, `build_progress`, etc.) return `true`.
- **Webhook `issue_comment` handler**: Mock the HTTP request/response cycle to verify correct routing based on comment content and workflow state.
- **Cron `isQualifyingIssue`**: Test with various comment combinations to verify correct qualifying logic.

### Integration Tests
- Verify that the webhook trigger correctly chains `isAdwComment` → `isAdwRunningForIssue` → `classifyIssueForTrigger` → `spawnDetached` for a human comment on an issue with no running workflow.
- Verify that the cron trigger skips (defers) qualifying issues when `isAdwRunningForIssue` returns `true` and re-evaluates them on the next poll cycle.

### Edge Cases
- A human comment that happens to contain a colon-wrapped word (e.g., "please check :the_file:") but not in a `## :emoji: ` heading format — should be treated as a human comment.
- Multiple human comments posted in rapid succession — the `processedIssues` set (cron) and response timing (webhook) should prevent duplicate workflow spawns.
- An issue where the ADW workflow errored out (`error` stage) followed by a human comment — should trigger a new workflow since the previous one has failed.
- An issue where the ADW workflow completed (`completed` stage) followed by a human comment — should trigger a new workflow since the previous one is done.
- A comment with `## :emoji:` but without a space after the closing colon — should NOT match the ADW pattern and be treated as human.

## Acceptance Criteria
- Both triggers (webhook and cron) correctly identify ADW-generated comments using the `## :emoji: ` heading pattern and ignore them.
- Both triggers correctly identify human comments (those without the ADW heading pattern) and trigger workflows for them.
- When an ADW workflow is already running for an issue (latest workflow stage is not `completed` or `error`), human comments are deferred — the triggers log the deferral and do not spawn a new workflow.
- The cron trigger re-evaluates deferred issues on subsequent poll cycles (does not permanently mark them as processed).
- All existing trigger functionality (issue opened, PR review comments, PR closure) continues to work without regression.
- All new and existing unit tests pass.
- `npm run lint`, `npm run build`, and `npm test` all pass with zero errors.

## Notes
- IMPORTANT: strictly adhere to the coding guidelines in `/guidelines`. If necessary, refactor existing code to meet the coding guidelines as part of implementing the feature.
- The ADW comment pattern `^## :[a-z_]+: ` is derived from the existing `STAGE_HEADER_MAP` in `workflowCommentsBase.ts` and the formatting functions in `workflowCommentsIssue.ts` and `workflowCommentsPR.ts`. All ADW comments use this `## :emoji_name: Title` format.
- The `isAdwRunningForIssue` function fetches the issue via `fetchGitHubIssue` which uses the `gh` CLI. This is consistent with existing patterns in the codebase (e.g., `fetchOpenIssues` in `trigger_cron.ts`). In the webhook trigger, this adds one API call per incoming human comment — acceptable given the low frequency of human comments.
- The deferral mechanism is intentionally simple: log and skip. There is no queuing or retry mechanism. The cron trigger naturally retries by re-evaluating on the next poll cycle (every 20 seconds). The webhook trigger relies on the cron trigger to eventually pick up the deferred comment.
- The `RawIssue` interface in `trigger_cron.ts` already includes `comments: { body: string }[]` which is sufficient for `isAdwComment` checks. No type changes are needed for the cron trigger's local interface.
