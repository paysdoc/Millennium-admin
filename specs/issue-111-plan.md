# Feature: Two-tier Issue Classification with ADW Keyword Detection

## Feature Description
Update the issue classification system to use a two-tier approach. A new `/classify_adw` command is added that first checks for specific ADW workflow keywords (e.g., `/adw_plan_build_test`, ADW IDs) in the issue body. Only when this keyword-based classifier returns no match (empty `{}`) does the system fall back to the existing LLM-based `/classify_issue` command. This reduces unnecessary LLM calls for issues that already contain explicit ADW workflow instructions, improving speed and cost-efficiency.

## User Story
As an ADW system operator
I want issues containing explicit ADW workflow commands to be classified instantly via keyword detection
So that classification is faster, cheaper, and more deterministic for ADW-generated issues

## Problem Statement
Currently, every issue — including those generated by ADW itself that already contain explicit workflow commands — is classified using the LLM-based `/classify_issue` command via Claude Haiku. This is wasteful because ADW-generated issues contain specific keywords (e.g., `/adw_plan_build_test`, ADW IDs) that can be detected deterministically without invoking an LLM. The current approach also cascades into self-referential issues (e.g., #107 -> #108 -> #109 -> #111) when the classifier cannot correctly identify ADW workflow context.

## Solution Statement
1. Add a new `.claude/commands/classify_adw.md` command that extracts ADW workflow commands and IDs from issue text using keyword matching, returning a JSON object with the detected command and ID, or `{}` if none found.
2. Update `adws/triggers/issueClassifier.ts` to first invoke `/classify_adw`. If it returns a valid ADW command, map it to the appropriate `IssueClassSlashCommand` and workflow script. If it returns `{}`, fall back to the existing `/classify_issue` LLM-based classification.
3. Add a new ADW command type mapping that converts ADW slash commands (like `/adw_plan_build_test`) to the existing workflow scripts.
4. Update `adws/core/dataTypes.ts` to include the new ADW command types and mapping.

## Step by Step Tasks

### Step 1: Add the `classify_adw.md` command
- Create `.claude/commands/classify_adw.md` with the ADW keyword extraction prompt.
- The prompt should:
  - Look for ADW workflow commands (e.g., `/adw_plan`, `/adw_build`, `/adw_plan_build_test`, `/adw_sdlc`, etc.)
  - Look for ADW IDs (8-character alphanumeric strings)
  - Return a JSON object `{ "adw_slash_command": "/adw_plan_build_test", "adw_id": "abc12345" }` if found
  - Return `{}` if no ADW workflow commands are found
- Include frontmatter with `name: classify_adw` and `description: Extract ADW workflow commands and IDs from issue text`.

### Step 2: Add ADW command types to `dataTypes.ts`
- Add an `AdwSlashCommand` type union with all valid ADW workflow commands (`/adw_plan`, `/adw_build`, `/adw_test`, `/adw_review`, `/adw_document`, `/adw_patch`, `/adw_plan_build`, `/adw_plan_build_test`, `/adw_plan_build_review`, `/adw_plan_build_document`, `/adw_plan_build_test_review`, `/adw_sdlc`).
- Add `AdwSlashCommand` to the `SlashCommand` union type.
- Add `'/classify_adw'` to the `SlashCommand` union type.
- Add an `adwCommandToWorkflowScript` mapping (`Record<AdwSlashCommand, string>`) that maps each ADW command to the appropriate workflow script path (e.g., `/adw_plan` -> `adws/adwPlan.tsx`, `/adw_plan_build` -> `adws/adwPlanBuild.tsx`, `/adw_plan_build_test` -> `adws/adwPlanBuildTest.tsx`).
- Add an `adwCommandToIssueClass` mapping (`Record<AdwSlashCommand, IssueClassSlashCommand>`) that maps ADW commands to their closest `IssueClassSlashCommand` for branch naming and commit prefixes (e.g., `/adw_plan_build_test` -> `/feature`).

### Step 3: Update exports in `core/index.ts`
- Export the new `AdwSlashCommand` type from `core/index.ts`.
- Export the new `adwCommandToWorkflowScript` and `adwCommandToIssueClass` mappings.

### Step 4: Update `issueClassifier.ts` with two-tier classification
- Add a new `AdwClassificationResult` interface with fields: `adwSlashCommand` (optional `AdwSlashCommand`), `adwId` (optional `string`), and `isEmpty` (`boolean`).
- Add a `parseAdwClassificationOutput()` pure function that parses the JSON output from `/classify_adw` and returns an `AdwClassificationResult`. Handle edge cases: malformed JSON, missing fields, empty object `{}`.
- Add a `classifyAdwKeywords()` async function that:
  1. Runs `/classify_adw` via `runClaudeAgentWithCommand()` with haiku model.
  2. Parses the output using `parseAdwClassificationOutput()`.
  3. Returns the `AdwClassificationResult`.
- Update `classifyIssueForTrigger()` to:
  1. First call `classifyAdwKeywords()` with the issue context.
  2. If the result has a valid `adwSlashCommand`, map it to an `IssueClassSlashCommand` using `adwCommandToIssueClass` and return success.
  3. If the result is empty (`{}`), fall back to the existing `/classify_issue` flow.
- Update `classifyGitHubIssue()` with the same two-tier logic.
- Update `getWorkflowScript()` to also accept `AdwSlashCommand` and use `adwCommandToWorkflowScript` when an ADW command is available, keeping the existing `IssueClassSlashCommand` path as fallback.
- Update the `IssueClassificationResult` interface to optionally include `adwSlashCommand` and `adwId` fields for richer downstream context.

### Step 5: Write unit tests for the classification system
- Create `adws/__tests__/issueClassifier.test.ts` with tests covering:
  - `parseAdwClassificationOutput()`:
    - Valid JSON with both `adw_slash_command` and `adw_id` fields.
    - Valid JSON with only `adw_slash_command`.
    - Empty object `{}` returns `isEmpty: true`.
    - Malformed/invalid JSON returns `isEmpty: true`.
    - Invalid ADW command string returns `isEmpty: true`.
  - `getWorkflowScript()`:
    - Each `IssueClassSlashCommand` maps to the correct script.
    - Default case returns `adwPlanBuildTest.tsx`.
  - `adwCommandToWorkflowScript` mapping:
    - `/adw_plan` maps to `adws/adwPlan.tsx`.
    - `/adw_plan_build` maps to `adws/adwPlanBuild.tsx`.
    - `/adw_plan_build_test` maps to `adws/adwPlanBuildTest.tsx`.
    - Other commands map correctly.
  - `adwCommandToIssueClass` mapping:
    - Each ADW command maps to the expected `IssueClassSlashCommand`.

### Step 6: Run validation commands
- Run `npm run lint` to check for code quality issues.
- Run `npm run build` to verify no build errors.
- Run `npm test` to validate the feature works with zero regressions.

### Integration Tests
- The existing trigger tests (`triggerCommentHandling.test.ts`) exercise the webhook and cron classification flows. These should continue to pass unchanged since the external interface is preserved.
- Verify that the `workflowPhases.ts` `initializeWorkflow()` function still works correctly with the updated classifier.

### Edge Cases
- Issue body contains multiple ADW commands (should pick the first valid one).
- Issue body contains an ADW ID but no command (should return partial match, fall back to `/classify_issue`).
- Issue body contains no ADW content at all (should return `{}`, fall back to `/classify_issue`).
- `/classify_adw` agent fails entirely (should gracefully fall back to `/classify_issue`).
- `/classify_adw` returns malformed non-JSON output (should treat as empty and fall back).
- Issue body is empty or null (should handle gracefully).
