# Chore: Set up local Supabase (DB + Storage) environment for Next.js application

## Chore Description
Implement a fully functional local Supabase environment (Postgres database + Storage bucket) for development purposes, enabling local feature development and testing without depending on the hosted Supabase project. This setup will use the Supabase CLI (Docker-based) to run Postgres and the Storage API locally, integrate with the existing Next.js application via environment variable switching, and commit migration files and Supabase configuration to version control. No application logic changes are required — the existing Supabase client in `src/lib/supabase.ts` already reads from environment variables (`SUPABASE_URL`, `SUPABASE_KEY`, `SUPABASE_SERVICE_KEY`), so only environment configuration and infrastructure files need to be created.

## Relevant Files
Use these files to resolve the chore:

- `src/lib/supabase.ts` — Supabase client factory; uses `SUPABASE_URL`, `SUPABASE_KEY`, and `SUPABASE_SERVICE_KEY` env vars. No changes needed, but validates that the app will connect to local Supabase when env vars point to `http://localhost:54321`.
- `src/lib/characters.ts` — Fetches from `character` table and uses `getSupabaseStorageUrl` for image URLs. Confirms the DB tables and storage path patterns the local environment must support.
- `src/lib/connections.ts` — Fetches from `connection` table. Confirms the `connection` table must exist locally.
- `src/lib/schema.ts` — Error handling utilities for tables and buckets. No changes needed.
- `src/types/character.ts` — Defines `CharacterRow` interface matching the `character` table schema (`id`, `name`, `first_names`, `birth_date`, `death_date`, `biography`, `type`, `link`, `image_link`).
- `src/types/connection.ts` — Defines `Connection` interface matching the `connection` table schema (`id`, `char1_id`, `char2_id`, `value`, `why`, `why_short`, `active`).
- `src/components/CharacterDetails.tsx` — Uses `Image` from `next/image` with `unoptimized` flag, so no Next.js image domain config is needed for localhost.
- `scripts/sync-config.ts` — Defines all tables to sync: `profiles`, `character`, `games`, `connection`, `game_players`, and the `character_images` storage bucket. This is the authoritative source for the production schema that must be replicated locally.

- `.env.sample` — Current env var template. Must be updated to document local Supabase values.

- `package.json` — Must add Supabase helper npm scripts.
- `README.md` — Must add local Supabase development instructions.

### New Files

## Step by Step Tasks
IMPORTANT: Execute every step in order, top to bottom.

### Step 1: Initialize Supabase CLI project
- Run `npx supabase init` from the project root to generate the `supabase/` directory with `config.toml`.
- This creates the foundation for local Supabase services. Do NOT start the services yet.
- Verify that `supabase/config.toml` was created.

### Step 2: Create the initial database migration file
- Create a new migration file at `supabase/migrations/<timestamp>_initial_schema.sql`.
- Use `npx supabase migration new initial_schema` to generate the timestamped file, then populate it.
- The migration must define these five tables matching production schema (derived from `scripts/sync-config.ts`, `src/types/character.ts`, and `src/types/connection.ts`):

**`profiles` table:**
```sql
CREATE TABLE IF NOT EXISTS profiles (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  username text,
  display_name text,
  full_name text,
  bio text,
  email text,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);
```

**`character` table:**
```sql
CREATE TABLE IF NOT EXISTS character (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  first_names text,
  birth_date text,
  death_date text,
  biography text,
  type text NOT NULL,
  link text,
  image_link text
);
```

**`games` table:**
```sql
CREATE TABLE IF NOT EXISTS games (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  created_by uuid REFERENCES profiles(id),
  created_at timestamptz DEFAULT now()
);
```

**`connection` table:**
```sql
CREATE TABLE IF NOT EXISTS connection (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  char1_id bigint NOT NULL REFERENCES character(id),
  char2_id bigint NOT NULL REFERENCES character(id),
  value integer,
  why text,
  why_short text,
  active boolean DEFAULT true
);
```

**`game_players` table:**
```sql
CREATE TABLE IF NOT EXISTS game_players (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  game_id bigint NOT NULL REFERENCES games(id),
  player_id uuid NOT NULL REFERENCES profiles(id),
  created_at timestamptz DEFAULT now()
);
```

- Note: The exact column types should be validated against the production schema. If the implementer has access to the remote database, they should run `supabase db pull` to get the exact schema and use that instead of these inferred definitions. The types above are best-effort inferences from the TypeScript interfaces and sync configuration.

### Step 3: Create the seed file for Storage bucket
- Create `supabase/seed.sql` with the following content to create the `character_images` storage bucket:
```sql
-- Create the character_images storage bucket (matches production)
INSERT INTO storage.buckets (id, name, public)
VALUES ('character_images', 'character_images', true)
ON CONFLICT (id) DO NOTHING;
```
- This ensures that when `supabase db reset` is run, the storage bucket is automatically created.
- The bucket name `character_images` matches production (confirmed in `scripts/sync-config.ts:78`).

### Step 4: Update `.gitignore` for Supabase
- Add entries to `.gitignore` to ignore Supabase-generated temporary/runtime files while keeping the config and migrations tracked:
```gitignore
# supabase
supabase/.temp/
supabase/.branches/
```
- Do NOT ignore the `supabase/` directory itself, `supabase/config.toml`, `supabase/migrations/`, or `supabase/seed.sql` — these must be version-controlled.

### Step 5: Update `.env.sample` with local Supabase documentation
- Add comments to `.env.sample` documenting the local Supabase values. Update the Supabase section to:
```env

# The deployment environment determines which database these point to.
#

#   SUPABASE_URL=http://127.0.0.1:54321
#   SUPABASE_KEY=<anon key from supabase status>
#   SUPABASE_SERVICE_KEY=<service_role key from supabase status>
#
# For PRODUCTION, Vercel sets these to the hosted Supabase instance.
SUPABASE_URL=
SUPABASE_KEY=
SUPABASE_SERVICE_KEY=
```
- Remove the `SUPABASE_BUCKET_NAME=` entry since it is not used anywhere in the application code.

### Step 6: Add npm scripts for Supabase CLI operations
- Add the following scripts to `package.json`:
```json
"supabase:start": "supabase start",
"supabase:stop": "supabase stop",
"supabase:reset": "supabase db reset",
"supabase:status": "supabase status"
```
- These provide convenient shortcuts and document available Supabase commands.

### Step 7: Update `README.md` with local Supabase setup instructions
- Add a new section to `README.md` (after the "Getting Started" section) titled "Local Supabase Setup" with instructions for:
  1. Prerequisites: Docker must be installed and running.
  2. Starting local Supabase: `npm run supabase:start` (or `supabase start`).
  3. Getting connection credentials: Run `npm run supabase:status` (or `supabase status`) to get the local `API URL`, `anon key`, and `service_role key`.
  4. Configuring `.env`: Copy the keys from `supabase status` output into `.env`:
     - `SUPABASE_URL=http://127.0.0.1:54321`
     - `SUPABASE_KEY=<anon key>`
     - `SUPABASE_SERVICE_KEY=<service_role key>`
  5. Resetting the database: `npm run supabase:reset` to apply all migrations and seed data.
  6. Stopping local Supabase: `npm run supabase:stop`.
  7. Note: The Supabase Studio UI is available at `http://127.0.0.1:54323` for visual database management.
  8. Note: Switching back to production requires updating `.env` with the hosted Supabase credentials — no code changes needed.

## Notes
- IMPORTANT: strictly adhere to the coding guidelines in `/guidelines`. If necessary, refactor existing code to meet the coding guidelines as part of accomplishing the chore.
- The application uses `SUPABASE_URL`, `SUPABASE_KEY`, and `SUPABASE_SERVICE_KEY` (server-side, no `NEXT_PUBLIC_` prefix). The GitHub issue mentions `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` but **these do not match the existing codebase**. The plan uses the actual env var names from the code.
- The `Image` component in `CharacterDetails.tsx` uses `unoptimized` prop, so no `next.config.js` image domain configuration is needed for `localhost`.
- The Supabase default local keys are deterministic — `supabase start` always produces the same anon key and service role key for a given project. This means the `.env` values only need to be set once per developer after initial `supabase start`.
- The migration SQL in Step 2 is a best-effort inference from TypeScript types. If the implementer has access to the remote Supabase project, they should prefer running `supabase db pull` to get the exact production schema instead of using the hand-written migration. The hand-written migration serves as a fallback.
- No application code changes are required. The Supabase client in `src/lib/supabase.ts` already reads all configuration from environment variables.
- Docker must be installed and running on the developer's machine for `supabase start` to work.
